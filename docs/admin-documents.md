# 문서 관리 화면

`DOC_ADMIN`·`SYSTEM_ADMIN`이 소스를 만들고, 문서를 올리고, 권한·버전을 관리하는 화면입니다. 서버(`Trace-Server` `develop`, PR #69 머지 시점)의 `/api/admin` API를 그대로 씁니다. 서버 변경이 필요한 기능은 넣지 않았습니다.

## 화면과 라우트

| 경로                   | 화면                                    |
| ---------------------- | --------------------------------------- |
| `/admin/documents`     | 문서 목록 (소스 선택·추가, 업로드 진입) |
| `/admin/documents/:id` | 문서 상세 (처리 상태, 권한, 개정, 삭제) |

- 두 라우트는 `AuthGuard` 안의 `AdminGuard` 아래에 있습니다. 역할이 `DOC_ADMIN`·`SYSTEM_ADMIN`이 아니면 `/`로 보냅니다. 화면 편의용이며 실제 권한은 서버가 판단합니다(403이면 "문서 관리 권한이 없습니다.").
- 사이드바의 "문서 관리"는 관리자 역할에게만 보이고, 현재 경로에 따라 "질문하기"와 "문서 관리" 중 하나가 선택 상태로 보입니다. 관리 화면에서는 채팅 패널을 표시하지 않습니다.
- 목록의 소스·처리 상태·유형·검색어·페이지는 URL 쿼리(`source`, `status`, `type`, `q`, `page`)에 둡니다. 상세에서 뒤로 가면 이전 필터로 돌아갑니다.
- 검색창에 입력하면 제목과 경로에 그 글자가 들어간 문서만 보여 줍니다. 서버 목록 API에 검색 조건이 없어, 같은 필터의 목록을 모든 페이지까지 받아 화면에서 거르고 20개씩 나눕니다. 문서가 아주 많아지면 서버 검색이 필요합니다.
- 목록 응답에 처리 상태가 없어 상태 열은 두지 않았습니다. 상태 필터로 걸러 보고, 문서별 상태는 상세에서 확인합니다. 상세는 처리 대기·진행 중이면 5초마다 다시 불러옵니다.

## 업로드

1. **파일 고르기**: 폴더 선택·파일 선택·드래그 앤 드롭. 고르는 즉시 서버와 같은 기준으로 미리 거릅니다(숨김 파일·폴더, `.obsidian/`·`.trash/`, `pdf`·`md` 외 형식, 20MB 초과, 빈 파일, 같은 경로 중복).
2. **권한과 정보**: 보안 등급(기본값: 소스 기본 등급), 열람 부서, 최소 직급, 소유 부서(기본값: 소스 기본 부서), 작성자, 작성일. 요청 안의 모든 파일에 같은 값이 들어갑니다.
3. **전송**: 파일 크기 합 90MB·50개 단위로 묶어 순서대로 보냅니다(서버 요청 한도 100MB에서 multipart 여유분을 뺌). 한 묶음이 실패하면 그 묶음 파일을 "전송 실패"로 표시하고 다음 묶음을 계속 보냅니다. 끝나면 실패한 파일만 다시 보낼 수 있습니다. 업로드·개정 요청은 시간 한도를 5분으로 따로 둡니다.
4. **결과**: 새 문서·새 버전·변경 없음·제외·전송 실패 요약과 파일별 결과 표.

업로드·개정·삭제·권한 수정이 끝나면 관리 화면뿐 아니라 질문 화면의 그래프 목록과 열려 있는 문서 탭(상세·처리 상태)까지 새로 받습니다. 원문 파일은 버전별로 내용이 고정되어 다시 받지 않고, 새 버전이 생기면 새로 받습니다. 그래서 문서 탭이 옛 버전이나 삭제된 문서를 계속 보여주지 않습니다.

개정 모달에서 작성자·작성일을 비우면 값을 보내지 않아 서버가 기존 값을 유지합니다. 비워서 지우려면 서버 개정 API에 "지우기" 의미가 정해져야 합니다(결정 필요).

경로 규칙: 폴더에서 고른 파일은 맨 앞 폴더명(고른 폴더 자체)을 뗀 경로를, 파일로 고른 파일은 파일명을 씁니다. 구분자는 `/`로 통일하고 앞의 `/`는 뗍니다. 경로가 곧 소스 안 문서 ID라서 같은 폴더를 다시 올리면 같은 문서의 새 버전이 됩니다.

## 서버 코드로 확인한 동작

구현 명세 7절의 확인 항목을 서버 코드(`DocumentService.uploadOne`/`upsertDocument`, `GlobalExceptionHandler`)로 확인한 결과입니다. 실제 실행으로는 아직 확인하지 않았습니다.

- **이미 있는 경로 업로드**: 내용(SHA-256)이 같으면 `UNCHANGED`이고 권한은 바뀌지 않습니다(작성자·작성일만 보낸 값으로 갱신). 내용이 다르면 새 버전을 만들고, 요청에 보낸 보안 등급으로 바뀝니다. 열람 부서는 보냈을 때만, 소유 부서도 보냈을 때만 바뀝니다. 최소 직급은 보내지 않으면 기존 값을 유지하므로 업로드로는 "제한 없음"으로 되돌릴 수 없습니다(권한 수정에서 바꿉니다). 업로드 모달 2단계에 이 내용을 안내합니다.
- **열람 부서를 비운 새 문서**: 서버는 열람 부서를 보내지 않으면 소스 기본 부서(`defaultDepartmentId`)만 열람하도록 만듭니다. 소스에 기본 부서가 없을 때만 전체 부서 열람입니다. 명세의 "비우면 전체 부서"와 다르므로 화면 안내를 서버 동작에 맞췄습니다.
- **새 버전 결과 값**: 서버 문서는 `UPDATED`가 있다고 하지만 현재 코드는 새 버전도 `CREATED`로 돌려줍니다. 화면은 `CREATED`이면서 `version`이 2 이상이면 "새 버전"으로 셉니다.
- **삭제 후 재업로드**: 삭제된 문서는 내용이 같아도 `UNCHANGED`로 건너뛰지 않고 새 버전을 만들며, `deleted_at`을 지우고 처리 job을 새로 만듭니다. 권한은 위의 "이미 있는 경로" 규칙과 같습니다. 실패한 문서를 다시 처리하는 우회 방법으로 상세 화면에 안내합니다.
- **요청 크기 초과**: 서블릿 한도를 넘으면 서버는 응답 봉투가 있는 `400 INVALID_INPUT`을 돌려줍니다. 앞단 프록시가 봉투 없는 `413`으로 끊는 경우는 클라이언트가 "업로드 크기 한도를 넘었습니다"로 바꿉니다.
- **상세의 소스 이름**: 상세 응답에 소스 이름이 없어 소스 목록에서 찾아 표시합니다. 소스 수가 적은 지금은 충분합니다.

## 결정 필요

- **macOS 한글 파일명(NFD)**: 경로를 정규화하지 않으므로, macOS에서 고른 한글 파일명은 NFD 그대로 경로가 됩니다. 시연 문서를 다른 방식(NFC)으로 이미 올렸다면 같은 문서가 다른 경로로 중복 생성될 수 있습니다. 서버와 함께 NFC 정규화 여부를 정해야 합니다.
- **경로에 쉼표가 있는 파일 1개 업로드**: Spring은 `paths` 값이 하나뿐이면 쉼표로 나눠 목록으로 바꿀 수 있어, 파일 수와 경로 수가 달라 400이 날 수 있습니다. 실제 실행으로 확인이 필요합니다.
- **직급 표시명**: 서버 시연 계정 이름에 맞춰 `STAFF` 사원, `MANAGER` 팀장, `DIRECTOR` 부장으로 표시합니다. `SENIOR`는 근거가 없어 임시로 "선임"입니다.
- **원문 다운로드**: 서버 다운로드 API가 인증 헤더를 요구해 새 창으로 바로 열 수 없으므로, 상세의 "원문 열기"를 "원문 다운로드"로 바꿨습니다. 누를 때 현재 버전 파일을 받아 원래 파일 이름(상대 경로의 마지막 부분)으로 저장합니다. 브라우저 안에서 PDF를 새 탭으로 여는 방식이 필요하면 파일 형식별로 안전하게 여는 방법(내용 형식 고정 등)을 함께 정해야 합니다.

## 넣지 않은 기능

문서 유형 수정, 폐지 상태, 휴지통·삭제 문서 복구 화면, 관계(그래프 연결) 편집, 시스템 관리(사용자·부서·Notion 토큰), 재처리 버튼, 파일마다 다른 권한, 표시 제목 입력, Notion 소스, 소스 수정·삭제는 서버 API가 없거나 MVP 범위 밖이라 넣지 않았습니다.

- 업로드 결과의 새 버전을 `UPDATED`로 구분(또는 `docs/api-guide.md`의 `UPDATED` 설명 수정)
- `docs/api-guide.md`의 "제목은 입력할 수 없다" 문구를 `titles` 지원에 맞게 수정
- (선택) 소유 부서를 비우는 방법, 업로드에서 최소 직급을 "제한 없음"으로 되돌리는 방법
